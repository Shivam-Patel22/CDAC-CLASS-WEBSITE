System Architecture DocumentComputer Class Website — Admin, Student & User Panel SystemV1 UPDATE: Student self-registration and login is now part of v1. A new `accounts` app has been added to own Student registration/login/dashboard, kept separate from the `dashboard` (admin) app. The Certificate model gains an optional link to a registered student account.1. OverviewThis document describes the technical architecture of the Computer Class Website, built using Django (backend + templating), HTML/CSS (structure and styling), and JavaScript (client-side interactivity where required). It follows Django's default MVT (Model-View-Template) pattern with a modular multi-app architecture, suitable for a small-to-medium institute website. Student self-registration and login are included in v1, in addition to the public site, certificate verification, and the admin panel.2. Certificate ID Generation StrategyTo keep certificate IDs unique and non-guessable:import uuid def generate_certificate_id():    year = timezone.now().year    unique_part = uuid.uuid4().hex[:6].upper()    return f"CERT-{year}-{unique_part}"Checked against existing Certificate.certificate_id values before saving (retry on collision, extremely rare).Displayed to the admin immediately after creation, to be shared with the student.Certificate ID generation is unrelated to student login — IDs are still admin-generated and never chosen or entered by the student.9. Project Rules & Development GuidelinesComputer Class Website — Admin, Student & User Panel SystemV1 UPDATE: Rules for the new accounts app (student registration/login/dashboard) have been added throughout this document, alongside a new Section 7 covering Student Account business rules.1. PurposeThis document defines the coding standards, naming conventions, workflow rules, and security rules to be followed while building this project. It ensures consistency across all Django apps (core, courses, certificates, accounts, dashboard) as defined in the Architecture document.2. General Coding RulesFollow PEP8 for all Python code (4-space indentation, snake_case for variables/functions, PascalCase for classes).Every Django app must have a single, clear responsibility (no mixing admin logic into public-facing apps, and no mixing student-account logic into the admin dashboard app).No business logic inside templates — templates only handle display; logic stays in views.py or models.py.Keep views thin: complex logic (e.g., certificate ID generation, student registration validation) should live in a helper/service function or a Django Form, not directly inside the view.Every model field must have a clear purpose — no unused/placeholder fields left in production code.Always use Django's ORM (Model.objects...) — never write raw SQL unless absolutely necessary.3. Naming ConventionsItemConventionExampleDjango appslowercase, pluralcourses, certificates, accountsModelsSingular, PascalCaseCourse, Certificate, StudentProfileViews (function-based)snake_case, verb-firstadd_course, verify_certificate, register, student_loginURL namessnake_case, app-prefixedcourses:course_list, accounts:register, accounts:dashboardTemplatessnake_case, .htmlcourse_list.html, register.htmlCSS classeskebab-case.course-card, .btn-primaryJS filescamelCase functionstoggleNavMenu()Certificate ID formatCERT-YYYY-XXXXXXCERT-2026-4F9A1B4. URL & Routing RulesEvery app has its own urls.py; the project's root urls.py only includes app URLs via include().All admin-only routes must live under the /admin-panel/ prefix (handled by the dashboard app).All student-account routes (register, login, logout, dashboard) live at the top level (/register/, /login/, /logout/, /dashboard/), handled by the accounts app, and must remain visually and structurally distinct from /admin-panel/  (New in v1).Public routes must never require login (core, courses listing, certificates verification).Use named URL patterns everywhere (name="course_list") — never hardcode URLs in templates; always use {% url %}.5. Authentication & Access RulesAdmin access is restricted to users with is_staff=True.Student access applies to any authenticated user with is_staff=False; students reuse Django's built-in User model rather than a separate custom user model  (Updated in v1).Every view inside the dashboard app must be decorated with @login_required and @staff_member_required (or the custom @staff_required decorator).Every view inside the accounts app that shows personal data (e.g., the dashboard view) must be decorated with @login_required  (New in v1).Never expose admin-only URLs in public or student navigation/templates.A student must never be able to reach /admin-panel/ routes, and an admin session must never grant access to another user's data on /dashboard/ (the student dashboard) — each view must filter by request.user  (New in v1).Passwords must never be stored or logged in plain text — rely entirely on Django's built-in auth hashing, for both Admin and Student accounts.CSRF protection ({% csrf_token %}) is mandatory on every form (public, student, and admin), including the registration and login forms.6. Certificate Rules (Business Logic)Certificate IDs must always be auto-generated by the system — never manually entered by the admin or the student, to avoid duplicates or predictable patterns.Certificate IDs must be unique and enforced at the database level (unique=True on the model field).Certificate verification is read-only for public users and students alike — visitors and students can never edit/delete a certificate from the verification page or the dashboard  (Updated in v1).Only an authenticated admin (is_staff=True) can add, edit, or revoke a certificate, or link/unlink it to a student account.A certificate must always be linked to an existing Course via ForeignKey — no certificate should reference a deleted/non-existent course (recommend on_delete=models.PROTECT to avoid accidental data loss).Linking a certificate to a student account (Certificate.student) is optional and admin-controlled; a student can never self-assign a certificate to their own account  (New in v1).The Student Dashboard query must always filter by Certificate.objects.filter(student=request.user) — never by name-matching alone, to avoid exposing another student's data  (New in v1).7. Student Account Rules (Business Logic)  (New in v1)Student registration requires a unique email address; Django's default validators plus a server-side uniqueness check must run before account creation.New student accounts are always created with is_staff=False and is_superuser=False — never grant elevated permissions through the public registration form.Password strength must be enforced via Django's built-in AUTH_PASSWORD_VALIDATORS — no custom weakening of these defaults.A StudentProfile record must be created alongside every new student User, in the same view/transaction, so the two never get out of sync.Students can only view their own certificates; there is no view or endpoint that lists another student's certificates.Students cannot edit their own certificate records, course enrollment status, or grade — those remain admin-only fields.There is no admin-approval step for new student accounts in v1 — registration is self-serve, consistent with the PRD.Session/login behavior for students uses the same django.contrib.auth session backend as Admin — no separate token/JWT system for v1.8. Course Rules (Business Logic)A course must have at least: name, description, and duration before it can be saved/published.Deleting a course that already has certificates issued against it should be restricted or warned (recommend on_delete=models.PROTECT in the Certificate.course field to prevent orphaned certificates).Course listing on the public page must only show fields meant for visitors (no internal-only fields, if added later).9. Frontend RulesAll pages must extend the shared base.html — no standalone HTML pages without the common navbar/footer, including the new register/login/dashboard templates.The navbar must conditionally show Register/Login (logged out) vs. Dashboard/Logout (student logged in) vs. Admin Panel (staff logged in), without ever mixing the three states  (New in v1).CSS must be written in the global static/css/style.css unless a page has truly unique styling needs (then scoped per-app).JavaScript should be used only where necessary (form validation, nav toggle, optional AJAX certificate check) — no JS frameworks, per the defined tech stack.All pages must be responsive (mobile + desktop) using CSS Flexbox/Grid — no fixed-width layouts.Images (course images, certificate templates) must be optimized before upload (reasonable file size, not raw uncompressed files).10. Security RulesNever disable Django's CSRF middleware.Never commit SECRET_KEY, database credentials, or DEBUG = True settings to version control for production.Use environment variables (.env + python-decouple or django-environ) for all sensitive settings.Sanitize all user input on forms (Django forms handle this by default — always use Django Form/ModelForm, never raw request.POST parsing without validation), including the student registration and login forms.Certificate ID lookups must use exact match queries only (no partial/wildcard search on the public verification page, to prevent enumeration attacks).Rate-limit or otherwise protect the login and registration views against brute-force / bot signups where feasible (e.g., Django's built-in login throttling, a CAPTCHA, or a simple honeypot field)  (New in v1).11. Git & Version Control RulesUse meaningful commit messages (e.g., feat: add certificate verification view, feat: add student registration, fix: course delete restriction).Never commit db.sqlite3, __pycache__/, .env, or media/ uploads to the repository — maintain a proper .gitignore.Work on feature branches (feature/certificate-verification, feature/student-login, feature/admin-course-crud) and merge into main/master only after testing.One feature/fix per commit where possible — avoid large, mixed-purpose commits.12. Testing RulesEvery model must have at least a basic test verifying creation and string representation (__str__), including StudentProfile.Certificate verification view must be tested for both valid and invalid Certificate IDs.Admin-only views must be tested to confirm they reject unauthenticated/non-staff users (redirect to login).Student registration must be tested for: successful signup, duplicate email rejection, and password-mismatch rejection  (New in v1).Student Dashboard must be tested to confirm: an anonymous user is redirected to login, and a logged-in student only ever sees their own certificates, never another student's  (New in v1).Run python manage.py test before every merge to main.13.
